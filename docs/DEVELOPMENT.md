# 제작 가이드라인

Shadow Mitts를 이어서 만들거나 고칠 때 지키는 원칙, 구조, 그리고 지금의 설계가 **왜** 이렇게 됐는지(측정 근거)를 정리합니다.
최초 기획은 [../DESIGN.md](../DESIGN.md).

---

## 1. 원칙

1. **확인 안 된 건 추측으로 코딩하지 않는다.** 외부 API는 설치된 패키지의 타입 정의(`.d.ts`)나 실제 실행 결과로 먼저 확인한다.
   좌표축처럼 문서에 없는 건 녹화 데이터로 재서 확정하고, 그 결과를 테스트로 고정한다.
2. **마일스톤 단위로 진행하고, 매번 사람이 웹캠으로 확인한다.** 인식 정확도·지연·체감은 자동화할 수 없다.
   "잘 된다"는 결론은 녹화 채점이나 플레이 테스트 결과가 있을 때만 내린다.
3. **임계값은 전부 placeholder.** 인식 임계값은 `src/core/params.ts` 한 곳에 모으고 화면 슬라이더로 노출한다.
   기본값을 바꿀 때는 녹화 채점(`npm run eval`) 결과를 근거로 남긴다.
4. **인식 로직은 카메라 없이 테스트할 수 있어야 한다.** `src/core/`는 DOM·카메라·MediaPipe에 의존하지 않는다.
   합성 포즈로 단위 테스트하고, 녹화 JSON을 재생해 회귀 테스트한다.
5. **판정은 이벤트 기반.** 손이 화면의 미트 좌표에 닿았는지는 보지 않는다(웹캠은 깊이를 못 봄).
   "어느 손 · 어떤 펀치 · 언제"만 본다. 미트를 어디에 그리는지는 순전히 보기 좋게 하기 위한 것.

## 2. 구조

```
카메라 ─▶ MediaPipe Pose (app/landmarker.ts → 별도 스레드 app/poseWorker.ts)
            │ 33개 랜드마크 (이미지 좌표 + 월드 좌표)
            ▼
        core/features.ts   One Euro 필터 → 팔 특징 (어깨 중점 기준, 몸통 길이 T 단위)
            ▼
        core/punch.ts      팔별 상태기계 → 펀치 이벤트 {시각, 손, 특징}
            ▼
        core/classify.ts   팔 자세 → 직선/훅/어퍼컷
            ▼
        core/game.ts       미트 출제 · 판정 · 점수 · 콤보         core/guard.ts  가드 판정
            ▼
        app/gameController.ts  화면 전환, HUD, 사운드 큐 ─▶ app/scene3d.ts (three.js 1인칭 장면)
```

## 3. 좌표와 단위 (M0에서 측정해 확정)

- **월드 좌표**: 원점 = 엉덩이 중점, +x = 사람의 왼쪽, +y = 아래, −z = 카메라 쪽. 이미지 좌표도 같은 방향.
  `tests/recordings.test.ts`가 녹화로 검증한다.
- **랜드마크 15/16은 사람 기준 왼/오른 손목.** 화면은 거울처럼 뒤집어 그리지만 데이터는 뒤집지 않는다.
- **깊이는 쓰지 않는다.** 카메라 쪽으로 잽을 뻗으면 월드 z·이미지 z가 오히려 뒤로 가고 3D 팔꿈치 각도가 75°→100° 정도로만 변했다.
- **기준점 = 양 어깨 중점, 단위 T = 몸통 길이**(어깨 중점 ~ 엉덩이 중점). 복싱 가드처럼 몸을 틀면
  MediaPipe가 두 어깨를 프레임마다 뒤바꾼다(가드 녹화에서 한쪽 어깨 x가 프레임 사이에 0.2씩 튐).
  한쪽 어깨 기준이었을 때는 가만히 있어도 펀치가 41번 잡혔고, 중점 기준으로 바꾸자 0번이 됐다.

## 4. 펀치 인식 설계와 근거

### 검출 (`core/punch.ts`)
팔마다 독립 상태기계: `대기 → 뻗는 중 → 복귀 중`.
- 가드에서 **빠르게 멀어지면** 시작, **가장 멀리 간 순간**을 펀치 시각으로 기록, 가드 근처로 **돌아와야** 다음 펀치.
- 걸러내는 움직임(모두 녹화에서 관찰됨):
  - 바깥/아래로 가는 움직임: 훅 예비동작, 어퍼컷 딥, 몸 회전에 끌려가는 가드 손
  - 아래로 향한 느린 움직임: 끌려가는 가드 손은 느리고, 아래 성분이 있는 진짜 펀치(크로스·훅)는 빠름.
    단 크게 휘두른 동작(0.2 T 이상)은 **주로 아래로** 갈 때만(아래 성분 > 이동의 30%, `punchDownFrac`) 이 규칙을 적용한다 —
    리드 훅은 끝에서 살짝 아래로 휘는데, 15fps에서 측정 속도가 3.4~3.9로 기준 4.0에 걸려 버려지고 있었다.
  - 바깥으로 0.15 T 넘게 가는 움직임은 버리되, **주로 위로 뻗으면** 바깥이 위쪽 이동의 40%까지 허용(`punchUpOutwardFrac`).
    게임의 잽 미트는 앞손 쪽에 있어서, 거기로 친 잽이 위로 0.73·바깥으로 0.22 가서 버려지고 있었다(게임 기록).
  - 너무 느리거나 오래 걸린 움직임(뻗는 시간 최대 480ms — 15fps에서는 프레임 간격 때문에 어퍼컷이 350~460ms로 재어진다)
- **낮은 fps 보정**: 프레임이 드물면 최고 속도가 낮게 측정된다. 최근 프레임 간격의 평균으로 속도 기준을
  30fps 이상은 그대로, 15fps에서는 0.75배(`lowFpsSpeedScale`)로 부드럽게 낮춘다.
  웹캠은 어두우면 스스로 15fps로 떨어진다(사용자 녹화가 60 → 30 → 15fps로 바뀐 것을 프레임 간격 16.7/33/67ms로 확인).
  60fps 녹화를 15fps로 솎아 재생하면 보정 전 100/175 → 보정 후 154/175, 오검출 0. `tests/recordings.test.ts`가 이 값을 지킨다.
- **어퍼컷 딥**: 뻗는 동안 가장 낮은 점을 따라가다가, 거기서 **위나 안쪽으로** 밀고 나가면 그 점부터 다시 잰다.
  작게 친 리어 어퍼컷은 2D에서 거의 올라오지 않고 낮은 높이에서 안쪽으로 밀고 들어가기 때문(녹화 "리어 어퍼컷 10회 작게").
  딥 뒤의 동작에는 별도 최소 속도(`dipDriveMinSpeed`, 1.0 T/s)를 쓰고, "아래로 향하면 빨라야 함"·몸통 회전 규칙은 적용하지 않는다
  (끌려가는 가드 손과 몸통 회전은 딥으로 시작하지 않는다).
- **몸통 회전 제거**: 양손이 화면에서 같이, 옆으로, 느리게(4 T/s 미만) 움직이면 펀치가 아니다.
  몸통 회전 녹화의 오검출은 공통 움직임 0.51~0.92였고 진짜 펀치는 대부분 0.45 이하였다.

### 추론은 별도 스레드 (`app/poseWorker.ts`)
첫 게임 기록: 메인 스레드에서 추론이 프레임마다 ~37ms × 초당 22회 = 시간의 ~80%를 차지해, 3D 화면이 그 틈에만 그려졌다
(화면 프레임 간격 중앙값 37ms, 최대 226ms — "끊기는 느낌"). Worker로 옮기고, 추론이 끝나면 새 카메라 프레임을 기다리지 않고
최신 프레임으로 바로 다음 추론을 시작한다. 헤드리스 비교(같은 조건, CPU): 화면 간격 중앙값 36.9 → 16.7ms, 추론 26.8 → 30회/초.
같은 이미지에서 메인 스레드와 Worker의 관절 좌표 차이 0. 주소에 `?mainthread`를 붙이면 예전 방식으로 돈다(비교용).
**기본은 CPU 추론**: 게임 중엔 3D 화면과 그래픽카드를 나눠 써서 GPU 추론이 느려졌다. 같은 PC·같은 난이도 두 판 비교:
GPU 65ms/프레임·초당 15회·PERFECT 12 / CPU 49ms·초당 20회·PERFECT 20. 개발자 도구의 "GPU로 인식"으로 바꿀 수 있다.
근거(규칙 1): 설치된 번들의 WASM 로더가 importScripts가 없으면 import()로 넘어가고, `forVisionTasks(base, true)`가
ES 모듈 WASM(`vision_wasm_module_internal.js`)을 고르며, GPU 그래프는 캔버스가 없으면 OffscreenCanvas를 만든다.

### 분류 (`core/classify.ts`)
주먹이 **어디서 멈췄는지(높이)**가 아니라 **팔 자세**로 판단한다(플레이 테스트에서 "높이로 맞춰 쳐야 한다"는 피드백).
- **훅**: 팔뚝(팔꿈치→손목) 각도가 누우면 훅. 녹화에서 훅 −12°~13°, 직선·어퍼컷 51° 이상으로 완전히 갈렸다.
  단, **딥으로 시작하면 훅이 아니다**(녹화된 훅 19개 중 딥 0개). 카메라를 향한 작은 어퍼컷은 팔뚝이 짧아 각도가 불안정하다.
- **직선 vs 어퍼컷**: 로지스틱 점수 = 팔뚝 길이(카메라 쪽 직선은 짧아 보임) · 팔꿈치 높이(어퍼컷은 낮음) · 딥 · 상승량.
  가중치는 녹화로 학습했고, 녹화 하나씩 빼고 검증하면 87/92(이전 높이 규칙 86/92).
- 게임 기록 4판(116펀치, 미트 번호를 정답으로)에서 86% (훅 32/34). 스트레이트↔어퍼컷 혼동이 대부분이고, 특징값 조합을 바꿔
  판 하나씩 빼고 검증해도 지금 규칙(게임 68/81)보다 나은 모델이 없었다 — 이 특징값으로는 여기가 한계라 더 맞추지 않았다.
- 한계: 학습 데이터의 어퍼컷 대부분이 딥을 동반해서, 딥 없는 어퍼컷은 팔꿈치가 확실히 낮고 크게 올라가야 인정된다.

| 지표 | 결과 |
|---|---|
| 가드만 / 몸통 회전만 한 구간의 오검출 | 0 |
| 친 손 + 시점 | 165/175 (94%) |
| 펀치 번호 | 160/175 (91%) |

알려진 약점:
- 25fps에서 빠른 연속 잽(1-1)은 화면상 0.12~0.15 T만 움직여 놓치기 쉽다.
  "최소 최고 속도"를 2.0→1.6으로 낮추면 1-1-2가 15/15로 오르지만 추가 검출이 9→18회로 늘어서 기본값은 2.0.
- 높은 크로스는 2D에서 크게 올라가 어퍼컷과 헷갈릴 수 있다.

## 5. 게임 규칙 (`core/game.ts`, 모두 placeholder)

- **미트 대 주기 판정**: 미트는 도착 후 `holdMs` 동안 머문다. `도착 − earlyMs` ~ `도착 + holdMs` 사이에 치면 맞음.
  `perfectMs`까지는 PERFECT, 이후 GOOD. (처음엔 ±160ms 한 순간이었지만 "실제 미트는 그렇게 안 친다"는 피드백으로 변경)
- **콤보 안에서는 다음 미트가 도착하면 앞 미트의 시간이 끝난다** (`Mitt.holdUntil` = min(도착 + hold, 다음 도착)).
  미트 잡이가 박자에 맞춰 미트를 바꾸는 것과 같다. 모든 미트는 **정해진 시각에만** 움직이고, 판정을 기다리지 않는다.
  (판정을 기다리게 했더니 한 번 늦게 치면 뒤 미트가 줄줄이 밀려 갑자기 튀어나오고 사라졌다 — 플레이 테스트.)

  | 난이도 | early | perfect | hold | 접근 시간 | 콤보 |
  |---|---|---|---|---|---|
  | 쉬움 | 300ms | 250ms | 1000ms | 2.6s | 1~2, 1~4번 |
  | 보통 | 250ms | 200ms | 750ms | 2.2s | 1~3 |
  | 어려움 | 200ms | 150ms | 550ms | 1.7s | 2~4 |

- 콤보는 손을 번갈아 쓰는 실제 복싱 콤보. 같은 손 연속은 1-1만.
- 반대 손 펀치는 무시(감점 없음). 같은 손 미트가 여럿이면 먼저 나온 미트부터 맞는다.
- 점수: PERFECT 100 · GOOD 60 · 부분 30, 10연속마다 ×0.1(최대 ×2), 가드 +20%.
- 미스 처리: `도착 + holdMs + 지연 보정 + 300ms`(검출 확정 지연)이 지나야 MISS.
- **지연 보정**: 판정에 `펀치 정점 시각 − 지연 보정`을 쓴다. 자동 보정은 8박자에 맞춘 펀치의 (정점 − 박자) 중앙값.

## 6. 3D 장면 (`app/scene3d.ts`)

- 1인칭(눈높이 1.6m), 화면 오른쪽 = 플레이어의 오른쪽. 미트 도착면은 1.7m 앞.
- 미트 표시 위치·각도 `PRESENT` (사우스포 기준, 오소독스는 좌우 반전) — 플레이 테스트 피드백으로 정함:
  1 잽 = 앞손 쪽·정면을 봄, 2 크로스 = 정중앙·몸이 도는 방향으로 틀어짐, 3·4 훅 = 옆·약 80°, 5·6 어퍼컷 = 아래·아래를 향함.
- 비행 경로도 종류별로 다르다: 직선 = 정면에서, 훅 = 옆에서 휘어 들어옴, 어퍼컷 = 아래에서 올라옴.
- 타이밍 단서: 반투명 목표 → 닫히는 링(도착 순간 금색) → 머무는 동안 남은 시간 게이지. 콤보 전 "틱·틱", 도착 "딱".
- **미트는 시계대로만, 멈춤 없이** (리듬 게임의 노트처럼): 모든 미트는 자기 경로를 일정한 속도로 날아와 제 시각에 도착한다.
  판정을 기다리거나 중간에 멈춰 대기시키는 방식은 둘 다 시도했다가 뺐다("늦게 치면 뒤 미트가 밀린다", "멈췄다 튀어나와 끊긴다").
- **같은 번호가 다시 나올 때**(2-3-2, 1-1 …): 앞 미트가 아직 있으면 뒤 미트는 옆·위로 비켜난 경로로, 처음부터 보이며 날아와 같은 목표에 도착한다.
  같은 경로 뒤에 숨기면 "같은 자리에 또 나옴", 앞 미트가 사라질 때까지 숨겼다 꺼내면 "친 게 또 뜬다"로 보였다(두 번째 게임 기록: 이런 반복 미트를 6번 중 4번 놓침).
  모든 미트는 0.2초 동안 커지며 등장한다.
- 링·목표 표시는 **지금 칠 미트 하나**(판정 전이고 시간 안에 있는 가장 이른 미트)에만.
- 맞은 미트는 제자리에서 부풀었다 0.16초 만에 사라지고, 시간이 끝난 미트는 제자리에서 줄어든 뒤 **다시 나타나지 않는다**
  (miss 판정은 늦게 도착하는 펀치를 기다리느라 0.3~0.5초 뒤에 난다). 폭발 글자 0.26초, 충격파 0.22초, 줌 킥은 작게.
- **판정된 미트가 되살아나던 버그**: 사라진 미트의 3D 모델을 지운 뒤, 목록에 남은 그 미트를 "모델이 없으니 새로" 만들어
  판정 전 상태로 몇 프레임 다시 그리고 있었다. 가상 시간으로 프레임마다 미트의 화면 위치를 기록하는 검사로 찾았다
  (카메라 없이 `__game.frame(t)`를 직접 돌림). 오래된 "잔상"·"갑자기 나타남"의 큰 원인이었다.
- 히트 스톱(타격 순간 정지)은 뺐다: 다른 미트까지 멈췄다가 건너뛰어 끊겨 보였다.
- 판정 안 된 미트의 3D 모델은 시간 창이 끝나는 순간 지운다. miss 판정까지 숨긴 채 남겨 두면 같은 번호의 다음 미트를 막고 있다가,
  지워질 때 다음 미트가 같은 자리에 불쑥 나타나 "놓친 미트가 다시 뜬다"로 보였다.
- **설정 저장은 바꾼 값만** (`shadowmitts.params.v2`): v1은 슬라이더 하나만 움직여도 전체 값을 저장해서, 이후 기본값 변경이 그 브라우저에 적용되지 않았다.
  두 번째 게임 기록을 예전 값(뻗는 시간 350ms)으로 재생하면 실제 판정과 34/34 일치 — 480ms 수정이 게임에 반영된 적이 없었다. v1은 한 번 지운다.
  게임 기록에 당시 설정(`params`, `paramsChanged`)도 함께 저장한다.
- **게임 기록 저장**: 게임 중 포즈 프레임을 메모리에 모아 두고, 결과 화면의 "이번 판 기록 저장"으로 내려받는다(영상 없음).
  일반 녹화 형식에 `game` 블록(미트 일정·판정, 화면 프레임 간격 `renderGapsMs`, 프레임별 추론 시간 `inferMs`)이 붙는다.
  "연습 녹화에선 되는데 게임에선 안 된다"를 게임 데이터로 직접 보기 위해.
- 글러브의 "빠르면 먼저 내밀기"는 **확실히 더 빠른 손**(2.5 T/s 초과, 반대 손의 2.5배)만 한다. 펀치 때 몸이 돌면 반대 손목도
  같이 움직여 엉뚱한 글러브가 찔끔 나갔다("오른손 어퍼컷에 왼손이 크로스"). 녹화 기준 반대 손 밀림 121 → 22회 / 216펀치.
- 카메라 창의 상태 표시가 인식 fps 20 미만이면 "인식 느림 (N fps) · 방을 더 밝게"로 바뀐다.
- 렌더 부하를 줄였다(픽셀 비율 최대 1.25, 그림자 PCF). 포즈 모델과 GPU를 나눠 쓰기 때문.
- 글러브: 손목을 따라 움직이고(약 1.15배), 손이 빠르면 인식 확정 전에 바로 앞으로 나간다.
- 모델은 전부 절차적(외부 3D 파일 없음). 배경 벽 사진만 이미지 파일(`public/assets/gym-bright.jpg`).

## 6-1. 타격감 (M3)

첫 버전은 "시원하지 않고 소리가 재미없다"는 플레이 피드백을 받아 강하게 다시 만들었다.

- **이펙트** (`scene3d.ts` `IMPACT`): 등급별 섬광·불꽃(PERFECT 70개)·충격파 링·미트 발광·찌그러짐, 작은 줌 킥(PERFECT −1.5°).
- **화면 연출** (`gameController.ts`): 만화풍 폭발 글자("빡!" "팡!" "BAM!" …)가 미트 위에서 튀어나옴, 화면 전체 하얀 번쩍임,
  10콤보마다 무지개 "N COMBO!"와 색종이.
- **타격감 2차** ("타격감이 좀 약하다", 화면 멈춤·큰 줌 없이): 카메라 **반동**(뒤로 밀렸다 돌아옴, 0.22초), 친 글러브만 미트에
  0.08초 박혀 눌렸다 돌아옴, 만화 **집중선** 0.13초, PERFECT 때 화면 테두리 금색 번쩍임, 저음 "쿵" 추가·친 쪽으로 소리 좌우 배치,
  콤보가 이어질수록 효과가 최대 +40%. 흔들림은 무작위 대신 부드러운 진동(~11Hz) — 무작위는 프레임마다 ~30px씩 튀어 떨림으로 보였다.
- **흔들림·번쩍임**: 카메라 흔들림 250ms 감쇠(PERFECT 0.065). 메뉴의 "흔들림·번쩍임" 스위치 하나로 둘 다 끈다(멀미·빛 민감).
- **소리** (`sfx.ts`, WebAudio 합성, 파일 없음): 타격음 = 낮은 쿵(피치 하강) + 딱(고역 노이즈) + 가죽 팡(대역 노이즈) + 음정 있는 "통",
  살짝 찌그러뜨리는 새추레이션과 짧은 울림(90ms). **연속으로 맞힐수록 음정이 반음씩 올라감**(MISS면 초기화).
  빗나감 = 만화 "뿅", 미트 없는 펀치 = "휙", 10콤보 = 드럼 + 팡파르(콤보가 쌓일수록 조 올림) + 관중 함성, 카운트다운 삑, 라운드 공.
- **외침**: 브라우저 음성(Web Speech)으로 "파이트!", 10콤보마다 "나이스!" "대박!" 등. PC에 한국어 음성이 없으면 조용히 생략.
- 판정 소리는 펀치 이벤트가 확정된 순간(펀치 정점 후 ~0.1~0.2초) 난다. 인식 지연이라 더 당길 수 없다.

## 6-2. 성장 요소 (M4)

- **적응형 출제** (`core/progress.ts`, 전부 placeholder): 펀치별 정확도(부분 점수는 절반)의 이동평균. 한 판에 n번 시도하면
  α = 1 − 0.88ⁿ만큼 새 정확도 쪽으로 이동. 출제 가중치 = 1 + 5 × (0.85 − 정확도), 0.6~3으로 제한. 3번 미만 시도한 펀치는 1.
  기존 `GameConfig.weights`(콤보 생성기)에 그대로 넣는다. 테스트: 약한 펀치가 1.8배 이상 자주 나옴.
  헤드리스 확인: 5번을 계속 놓치게 하면 다음 판에 5번 비율 18% → 35%.
- **약점 리포트**: 이번 판에 눈에 띄게 약한 펀치(다른 펀치와 15%p 이상 차이) + 누적으로 가장 약한 펀치(나머지 평균보다 10%p 이상 낮을 때만).
- **로컬 기록** (`app/records.ts`, `shadowmitts.progress.v1`): 펀치별 실력, 최근 50판, 난이도별 최고 점수. 전부 try/catch —
  저장이 막히면 결과 화면에 알려 주고 게임은 계속. 저장값은 `sanitizeProgress`로 검사해서 깨진 값은 버린다.
- **결과 카드** (`app/resultCard.ts`): 1080×1350 PNG(SNS 세로형), 페이지 글꼴이 로드된 뒤 캔버스에 그림.
  칼로리 같은 근거 없는 추정치는 넣지 않음(DESIGN §5). 얼굴은 스위치가 켜져 있을 때만.

## 7. 테스트와 튜닝

```bash
npm test                  # 전체 (합성 + 녹화가 있으면 녹화 회귀)
npm run eval              # 녹화 채점 표
npm run eval -- -v        # 펀치 하나하나의 특징값
npm run eval -- --mirror  # 좌우 반전 데이터까지
```

- **합성 테스트** (`tests/punch.test.ts` 등): `trajectory()`로 손목·팔꿈치 궤적을 만들어 검출·분류·판정을 검증.
  실제 녹화의 속도 범위(잽 2~3.6 T/s 등)에 맞춰 만든다.
- **녹화 회귀** (`tests/recordings.test.ts`): 녹화가 있으면 오검출·검출률·번호 정답률 하한을 검사. 하한은 측정값보다 조금 낮게.
- **녹화 방법**: 개발자 도구 → 녹화. 메모 규칙은 [../recordings/README.md](../recordings/README.md).
  약점을 고칠 때는 그 동작만 따로 녹화(예: `사우스포, 콤보 1-1-2 5회`)해서 원인을 먼저 보고 고친다.
- **튜닝 순서**: ① 녹화로 재현 → ② `eval -v`로 특징값 확인 → ③ 슬라이더/파라미터 스윕 → ④ 오검출·검출률·정답률을 함께 보고 기본값 결정 → ⑤ 테스트 하한과 문서 갱신.

## 8. 코드 규칙

- `src/core/`에는 DOM·브라우저 API를 넣지 않는다.
- 새 임계값은 `params.ts`에 추가하면 슬라이더가 자동으로 생긴다. 기본값 옆에 근거(측정값)를 주석으로.
- 판정·인식 로직을 바꾸면 테스트를 같이 바꾸고, 녹화 채점 결과를 이 문서에 남긴다.
- localStorage 접근은 항상 try/catch (시크릿 모드 등에서 실패해도 동작).
